# Test Strategy

## 本リポジトリとの関係

- **正本**: この Skill（観点表・リスク・テストレベル選択）
- **TDD 手順**: `test-driven-development` Skill（自動化可能な振る舞い変更時）
- **適用規則**: `AGENTS.md` Coding conventions

新規機能は `test-strategy` で観点を整理したうえで、自動化対象のケースは TDD で実装する。

## 目的

変更によって壊れ得る振る舞いを明確にし、テスト観点の漏れを防ぎながら、保守性の高い自動テストを実装する。

カバレッジ値そのものを目的化せず、次の順序で品質を確保する。

1. 仕様・期待される振る舞いを理解する
2. 変更によるリスクと影響範囲を特定する
3. テスト観点を体系的に洗い出す
4. 最も適切なテストレベルで検証する
5. テストを実行し、結果と未検証リスクを確認する
6. 観点漏れがないか自己レビューする

---

## 適用対象

以下の場合はこのSkillを使用する。

- 新機能を実装する
- 既存仕様を変更する
- バグを修正する
- バリデーションや権限制御など、新しい制約を追加・変更する
- 外部API、DB、メッセージング、ファイルI/Oなどとの連携を変更する
- 挙動に影響し得るリファクタを行う
- 不足している既存テストを追加する

次の場合は、テスト観点表の新規作成・更新を省略してよい。

- テストコードのみの軽微な修正
- テスト名やコメントの修正
- 仕様・分岐・制約に影響しない期待値表現の変更

ただし、省略する場合でも変更が新しい振る舞いを生んでいないことを確認する。

# Workflow

## Step 0. 仕様・既存実装・既存テストを確認する

テストコードを書き始める前に、最低限以下を確認する。

- 対象機能の仕様または受け入れ条件
- 変更差分と影響範囲
- 既存のテストコードとテスト規約
- 使用しているテストフレームワーク
- テスト実行コマンド
- カバレッジ取得方法
- 外部依存の有無

既存コードの振る舞いと仕様が食い違う場合は、既存実装を正として暗黙にテストを固定しない。仕様上どちらが正しいかを確認し、判断できない場合は不明点として明示する。

バグ修正では、可能な限り最初に不具合を再現する失敗テストを追加し、そのテストが修正前に失敗し修正後に成功することを確認する。

---

## Step 1. テスト観点表を作成する

原則として、テスト実装前に Markdown 形式のテスト観点表を提示する。

最低限、以下の列を含める。

| Column | Description |
|---|---|
| `Case ID` | テストケース識別子 |
| `Input / Precondition` | 入力値・状態・前提条件 |
| `Perspective` | 等価分割、境界値、異常系などの観点 |
| `Expected Result` | 外部から観測可能な期待結果 |
| `Notes` | 補足、対象外理由、未自動化理由など |

必要に応じて以下の列も追加する。

- `Risk`: High / Medium / Low
- `Test Level`: Unit / Integration / E2E
- `Automation`: Automated / Manual / N/A

### テンプレート

| Case ID | Input / Precondition | Perspective | Expected Result | Risk | Test Level | Notes |
|---|---|---|---|---|---|---|
| TC-N-01 | Valid input A | Equivalence - normal | 処理に成功し期待値を返す | High | Unit | - |
| TC-A-01 | NULL | Boundary - NULL | 必須入力エラーになる | High | Unit | - |
| TC-B-01 | upper limit + 1 | Boundary - upper + 1 | 上限超過エラーになる | Medium | Unit | - |

### 観点設計ルール

正常系・異常系・境界値を機械的な件数ではなく、仕様・分岐・リスクに基づいて網羅する。

最低限、次の候補を検討する。

#### 等価分割

- 代表的な正常入力
- 代表的な不正入力
- 状態・権限・種別ごとの主要な振る舞い

#### 境界値

仕様上意味を持つ場合、以下を検討する。

- `0`
- 最小値
- 最小値の直前 / 直後
- 最大値
- 最大値の直前 / 直後
- 空文字列
- 空配列 / 空オブジェクト
- `NULL` / `undefined` 相当

候補のうち仕様上意味を持たないものは、無理にテストを作らず `Notes` に対象外理由を書く。

#### 入力異常

該当する場合は以下も検討する。

- 不正な型
- 不正な形式
- 桁数超過
- 未知のenum値
- 重複値
- 不正な文字コード・特殊文字
- 不正な日時・タイムゾーン

#### 状態・副作用

該当する場合は以下も検討する。

- DB更新結果
- トランザクション境界
- 二重実行・冪等性
- リトライ
- タイムアウト
- 部分失敗
- ロールバック
- キャッシュ有無
- イベント・メッセージ送信
- 並行実行・競合

#### セキュリティ・権限

該当する場合は以下も検討する。

- 未認証
- 権限不足
- 他ユーザー / 他テナントのデータへのアクセス
- 入力値を経由したインジェクション等の代表的な攻撃パターン

観点表作成後、仕様の条件分岐・入力制約・状態遷移と照合し、漏れを自己レビューする。
後から漏れに気づいた場合は、観点表を更新してからテストを追加する。

---

## Step 2. 適切なテストレベルを選択する

すべてをUnit Testで解決しようとしない。

検証したいリスクに対して、最も低コストで十分な信頼性を得られるテストレベルを選択する。

### Unit Test

主に以下を検証する。

- 純粋なビジネスロジック
- 入力バリデーション
- 分岐条件
- 値変換
- ドメインルール

### Integration Test

主に以下を検証する。

- DBとの実際の連携
- ORM・SQL・スキーマ制約
- HTTPクライアントやキューなどの境界
- フレームワーク設定
- 複数コンポーネント間の連携

### E2E Test

主に以下を検証する。

- ユーザーにとって重要な主要シナリオ
- 複数レイヤを跨ぐ重要フロー
- Unit / Integration Testだけでは保証できないシステム境界

同じ振る舞いを複数レベルで過剰に重複検証しない。
E2Eは主要フローを中心とし、詳細な組み合わせはUnit / Integration Testへ寄せる。

---

## Step 3. テストコードを実装する

観点表に記載したケースは原則として自動化する。

自動化が合理的でないケースは無理に自動テスト化せず、以下を `Notes` またはPR本文に記載する。

- 自動化できない理由
- 対象機能とリスク
- 代替となる検証方法
- 手動検証手順
- 期待結果
- 証跡となるログ・スクリーンショット等の保存方法

### 必須観点

対象仕様に存在するものについて、以下を検証する。

- 正常系の主要シナリオ
- 異常系
- 境界値
- バリデーションエラー
- 例外経路
- 不正な型・形式
- 外部依存の成功 / 失敗
- 状態変化と副作用
- バグ修正時の回帰ケース

異常系の件数を正常系と機械的に同数以上にする必要はない。
ケース数ではなく、実装に存在する意味のある失敗経路と、ビジネスインパクトの高いリスクが検証されていることを優先する。

---

## Step 4. Given / When / Then で意図を明確にする

各テストは Given / When / Then の構造が読み取れるようにする。

必要に応じて以下のコメントを使用する。

```text
// Given: 前提条件
// When:  実行する操作
// Then:  期待する結果 / 検証
```

ただし、テストフレームワークの `given/when/then` DSL、明確なテスト名、Arrange / Act / Assert 構造などによって意図が十分に明白な場合、冗長なコメントを機械的に追加する必要はない。

コメントを書く場合は「コードを読めば分かる処理内容」ではなく、「なぜその前提・期待値になるのか」を優先して記述する。

---

## Step 5. 例外・エラーを検証する

異常系では、実装詳細ではなく外部契約として意味のある情報を検証する。

優先順位は以下とする。

1. エラー種別 / 例外型
2. エラーコード
3. 対象フィールド
4. HTTPステータス等の外部契約
5. 必要に応じてエラーメッセージ

エラーメッセージ全文の完全一致は、その文言自体がAPI契約・UI仕様・業務要件である場合に限定する。
文言が実装詳細である場合は、エラーコードや構造化された情報を優先し、壊れやすいテストを避ける。

---

## Step 6. 外部依存をテストする

API / DB / メッセージング / ファイル / 時刻 / 外部サービス等への依存がある場合、必要に応じてテストダブルを利用する。

テスト対象に応じて以下を使い分ける。

- Fake
- Stub
- Mock
- Spy
- Test Container
- ローカルエミュレータ

### 外部依存の失敗系

該当する場合、以下を検証する。

- エラー伝播
- エラー変換
- タイムアウト
- リトライ
- フォールバック
- ロールバック
- 部分成功 / 部分失敗
- 冪等性

外部依存が存在しないコードに対して、失敗ケースを作る目的だけで不自然なモックを導入しない。
失敗経路が入力や状態によって発生するのであれば、その実際の境界を使って検証する。

モックの呼び出し回数や内部メソッドの呼び出し順序など、実装詳細への過剰な依存は避ける。
ただし、それ自体が契約となる副作用や、重複送信防止などで呼び出し回数が重要な場合は明示的に検証する。

---

## Step 7. カバレッジを確認する

テスト実装後に、プロジェクトで利用可能な範囲で以下を確認する。

- Branch Coverage
- Statement Coverage
- Function / Method Coverage
- Line Coverage

分岐網羅率 100% は目標値として扱うが、完了条件そのものにはしない。

特に優先して網羅する。

- ビジネスインパクトの高い分岐
- セキュリティ・権限に関わる分岐
- データ損失につながる分岐
- 外部サービス障害時の経路
- 過去に不具合が発生した経路
- 複雑度の高い条件分岐

カバレッジを上げるためだけの意味のないアサーションや、実装をなぞるだけのテストを追加しない。

未カバーの意味のある分岐が残る場合は、理由と影響を `Notes` またはPR本文に記載する。

必要に応じて、カバレッジでは検出しにくい弱いテストを確認するため Mutation Testing の利用も検討する。

---

## Step 8. テストを実行する

変更したテストだけでなく、影響範囲に応じて関連テストも実行する。

最低限、以下を記録する。

```text
Test command:
<実行したコマンド>

Coverage command:
<カバレッジ取得コマンド。利用できない場合はその旨>

Result:
<成功 / 失敗、テスト件数、必要に応じて主要なカバレッジ値>
```

例:

```text
Test command:
uv run pytest tests/test_search_service.py

Coverage command:
（本リポジトリでは pytest-cov 未設定のため省略可）

Result:
12 passed
```

テストを実行できない環境の場合は、実行したと偽ってはならない。
実行できなかった理由と、ユーザーまたはCIで実行すべきコマンドを明示する。

---

## Step 9. Self Review

テストタスクを完了する前に、以下を自己確認する。

### 仕様

- [ ] 変更された仕様・受け入れ条件を把握している
- [ ] 変更によって影響する既存仕様を確認した
- [ ] バグ修正の場合、再現テストまたは同等の回帰テストがある

### テスト観点

- [ ] 正常系を確認した
- [ ] 異常系を確認した
- [ ] 意味のある境界値を確認した
- [ ] NULL / 空 / 0 / min / max / ±1 の適用可否を検討した
- [ ] 状態遷移・副作用を確認した
- [ ] 外部依存の失敗経路を確認した
- [ ] 権限・セキュリティ観点の適用可否を確認した

### テスト品質

- [ ] テスト名から期待する振る舞いが理解できる
- [ ] 1つのテストが過剰に多くの振る舞いを検証していない
- [ ] 実装詳細ではなく外部から観測可能な振る舞いを優先している
- [ ] 過剰なモックを使用していない
- [ ] テスト間に不要な依存がない
- [ ] テスト結果が実行順序・実時刻・外部環境に不必要に依存しない
- [ ] 意味のないカバレッジ稼ぎをしていない

### 実行結果

- [ ] 対象テストを実行した
- [ ] 必要な関連テストを実行した
- [ ] カバレッジを確認した、または確認できない理由を記載した
- [ ] 未カバーの重要な分岐があれば理由とリスクを明示した

# テスト実装ポリシー

## 振る舞いをテストする

テストは「どのように実装されているか」ではなく、「入力・状態に対して何が起きるべきか」を優先して検証する。

避ける例:

- privateメソッドを直接テストする
- リファクタだけで壊れる内部呼び出し順序を検証する
- モックの呼び出しを確認するだけで結果を検証しない

推奨する例:

- 戻り値
- 永続化された状態
- 公開APIのレスポンス
- 発行されたドメインイベント
- ユーザーから観測可能なエラー

---

## テストは決定的にする

テストは同じコードに対して安定して同じ結果を返すようにする。

以下へ直接依存する場合は制御可能な形へ置き換えることを検討する。

- 現在時刻
- 乱数
- ネットワーク
- 実行順序
- グローバル状態
- OS固有状態

`Date.now()`、乱数、外部APIなどを固定できる設計であれば固定する。

---

## テストデータは意図を明確にする

巨大なfixtureを無条件に再利用せず、そのテストで重要な値が分かるようにする。

Builder / Factoryを利用する場合も、テスト結果に影響する値はテスト内で明示する。

---

## 本番コード変更時のルール

原則として、以下の変更を含むPRには対応する自動テストの追加または更新を含める。

- 仕様追加
- バグ修正
- 挙動変更
- 挙動に影響し得るリファクタ

挙動変更を意図しないリファクタの場合も、変更箇所が既存テストで十分に保護されているかを確認する。
不足していれば、リファクタ前または同時に Characterization Test / Regression Test を追加する。

テスト追加が合理的に困難な場合は、理由・リスク・代替検証手順をPR本文に記載する。

---

# Completion Criteria

以下を満たしたとき、テストタスクを完了とする。

1. 仕様と変更影響を確認した
2. 必要なテスト観点表を作成・更新した
3. リスクに応じた適切なテストレベルを選択した
4. 重要な正常系・異常系・境界値・回帰ケースを実装した
5. 必要な外部依存失敗ケースを検証した
6. テストを実行した、または実行できない理由を明示した
7. カバレッジと未検証リスクを確認した
8. Self Reviewを完了した
9. テスト実行コマンドと結果を提示した

テスト件数やカバレッジ率だけで完了と判断してはならない。
最終的な完了判断は、変更による主要なリスクがテストによって十分に抑えられているかで行う。
